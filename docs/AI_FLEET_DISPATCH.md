# AI 集群调度第一版

2026-10-19更新：预览已加入禁飞/限高区的完整预计航线与生效时间检查，候选违规原因可解释；确认方案与实际起飞各自复查最新规则。新增能力与验收见 `AIRSPACE_SAFETY_V1.md`。下文“没有禁飞区”的描述保留为2026-10-18交付时边界，不代表当前状态；两机冲突与调机飞行仍未实现。

交付日期：2026-10-18。入口为平台顶部“Agent指挥” → “AI 集群调度”，地址 `http://127.0.0.1:5173/agent-command`。

本版实现多飞行器、多任务的可解释约束优化和人工确认批量派机，使用 Java 最小费用最大匹配算法 `fleet-mincost-v1`。不需要模型 API 密钥，也没有调用大语言模型、训练模型或创建另一套任务状态。自然语言 Agent 可在后续调用同一接口。

## 使用

1. 在物流运输创建配送订单，或在任务管理创建仿真任务，保持“待分配”。
2. 打开 Agent 指挥，选择本批任务、每项优先级及参与评估的飞行器。
3. 生成方案，核对分配结果、评分、候选排除原因和就近派机基线。
4. 点击“确认批量派机”，填写原因。后端重新校验当前状态，在同一事务中完成分配。
5. 前往任务管理执行仿真；物流订单页会从同一关联任务读取派机与飞行状态。

只读账号可以查看历史方案；生成、确认要求 `sky:operate`。同一批最多20项任务、200架飞行器，每架飞行器最多分配一个任务。资源不足的任务进入方案的等待资源结果，不自动排未来班次、不抢占执行中任务。

## 优化目标和约束

按以下顺序求解：

1. 最大化本批可分配任务数量。
2. 在数量相同的方案中，最大化已选任务的优先级数值之和。
3. 在前两项目标相同的方案中，最小化综合成本。

普通/优先/紧急对应1/2/3，只保存在本次调度方案里，不改变任务的长期优先级。

硬约束包括：任务仍为created、飞行器idle且未移除、站点可用；物流用cargo、通勤用座位足够的eVTOL、其他任务不用eVTOL；载重不超限；电量不低于 `max(25, durationSeconds × 0.08 + 20)`；关联物流订单的预计仿真到达时间不晚于截止时间。手动派机、订单派机和集群确认共用 `DispatchOptimizer.constraintReasons`，起飞再次复查。

飞行器与任务的成本为：

```text
距离成本 = 45 × min(飞行器至起点的球面距离 / 20000米, 1)
电量成本 = 35 × clamp((100 − 当前电量 + 任务仿真耗电) / 100, 0, 1)
运力成本 = 20 × (1 − 任务载重 / 飞行器载重上限)
通勤的运力成本使用人数 / 座位数；零载重普通任务使用无人机成本0、货运机成本20。
综合成本 = 距离成本 + 电量成本 + 运力成本
评分 = 100 − 综合成本
```

运力成本限制为0～20。成本以0.01为精度求解。预计耗电为 `durationSeconds × 0.08` 个电量百分点，沿用项目已有简化仿真规则，不是物理能耗或真实机型续航。

算法构造“源点 → 任务 → 飞行器 → 汇点”二分图，仅为可行组合建立边。残余反向边允许撤销先前局部选择并重新匹配。持续寻找最短增广路径直到无法再分配，保证最大匹配；任务优先级成本以大于全部任务成本的权重编码，随后优化组合成本。

基线使用相同任务、资源和硬约束，按优先级降序、任务ID升序逐项分配最近的空闲飞行器。不同分配数量的方案应先比较数量、再比较优先级和成本，不能用“分配更少因而总成本更低”宣称基线更优；单批结果也不代表算法普遍收益。

## 持久化和并发

`st_dispatch_plan` 保存请求、完整候选/评分、算法版本、创建人、有效期、确认人、确认时间和原因。生成方案只写方案和预览审计，不锁定业务资源；有效期5分钟。

确认时先锁方案，按稳定顺序锁任务再锁飞行器，随后逐项调用原 `SkyService.taskAction(...,"assign",...)`。资源状态或电量已变、任务被取消、时限不足等均拒绝执行。任何一项或末尾审计写入失败都会回滚整批任务、飞行器状态及方案确认状态。两份不同方案争抢同一资源时，由飞行器行锁和最新状态复查保证仅一份成功。已确认方案再次提交返回409。

API：

| 方法 | 路径 | 作用 |
|---|---|---|
| POST | `/sky/dispatch/plans` | `{tasks:[{taskId,priority}],aircraftIds?:string[]}` 生成方案；省略资源列表时评估全部未移除资源 |
| GET | `/sky/dispatch/plans` | 最近20条历史 |
| GET | `/sky/dispatch/plans/{id}` | 保存的方案、请求、服务端时间 |
| POST | `/sky/dispatch/plans/{id}/confirm` | `{reason}` 原子批量派机 |

## 工程结构

- `DispatchOptimizer.java`：不依赖Spring的约束、成本、全局匹配和基线。
- `DispatchService.java`：读取业务快照、保存方案、加锁确认和审计。
- `DispatchController.java / DispatchInputs.java`：鉴权HTTP入口与参数校验。
- `shared/dispatch.ts`：前端共享返回类型。
- `useFleetDispatch.ts`：请求、过期计时、提交结果和卸载清理；分配成功后的刷新失败不会被报告成派机失败。
- `FleetDispatchWorkspace`：组合任务选择、方案结果、候选/确认弹窗和历史组件；路由页保持薄组件。
- `sky_twin_v3_dispatch.sql`：仅新增方案表，已纳入 `migrate-sky.ps1`。

## 当前边界和下一步

这是单轮资源分配优化，不是长期任务排程、真实无人机集群飞控或实机避障。距离为资源到起点的评分项；当前仿真起飞依旧在任务起点定位，未模拟调机航程，也未把调机耗电或耗时计入物流截止判断。没有禁飞区/两机时空冲突算法，不能宣称当前方案已完成空域安全放行。

下一步接入航点与空域规则后，应把调机/任务路径、时间窗与能耗统一进候选约束；自然语言Agent负责受控调用这些服务。可选学习点：解释为什么“每项任务选最近飞行器”会占掉其他任务唯一可用的资源，并对照上述固定反例观察全局重匹配。
