## 3. 建议产品主张

保留SkyTwin品牌与现有底座，把比赛核心聚焦为“面向低空巡检的AI协同处置工作台”。核心用户是需要复核发现、制定侦察方案和追溯处理结果的操作员。

主线：影像分析 → 人工复核来源/位置/等级 → 业务事件 → Agent查实时资源与规则、生成可解释方案 → 人工确认 → Java重新验收并仿真执行 → 证据归档及事实摘要。

创新点应接受验证：把影像证据、领域依据、实时资源和空间约束连接在同一工作流；地图/图片/方案卡与对话共同交互；模型提出建议、业务规则验收、操作者确认，结果可追溯。

物流保留为成熟业务和Agent首个小步的练习载体。时间紧时先跑通自然语言物流方案，再复用工具机制接巡检事件；不要同时扩建物流、通勤、救援等多条新状态机。

## 4. 必做事项及验收

### P0-A：先恢复入口与真实模型最小验收

- 恢复环境发现的新建/复核入口；保留离线巡逻与历史discoveryId链接的清晰入口。
- 用真实模型验证一次机队查询、一次规则引用、一次无依据拒答，区分当前网页结果与旧截图。
- 解决主线按钮无反馈、超时不明、页面刷新丢失上下文等实际阻塞。北斗不在主线时优先级降低。
- 验收：从普通导航能新建发现；不依赖手写历史URL；空数据、失败、权限不足均有明确反馈；服务端拒绝越权和非法状态变更。

### P0-B：Agent生成方案并呈现可确认卡片

- 增加只读任务/订单/事件及资源查询、受限的方案预览工具，复用Java鉴权接口。
- LLM提取目标、查询数据、解释约束；原Java优化器负责匹配，原业务服务负责状态。
- 网页渲染结构化任务、机队、地图航线、未分配原因、规则来源及确认动作；执行结果引用实际业务ID。
- 保存当前会话选中事件/任务及方案ID，先实现受限指代，不急于长期记忆或多个Agent。
- 验收：对象缺失先追问；方案能打开对应地图/任务；资源已变动时旧方案拒绝；只读账号不能确认；重复确认不重复分配；模型超时不显示执行成功。
- 模型工具链不直接触发起飞，确定性UI确认后走原Java校验。不得用模型判断替代电量、占用、空域和时空冲突检查。

### P0-C：影像分析进入人工业务闭环

- 接受合法授权用户图片，建立独立分析记录：原图哈希、模型版本、框、阈值、结果与时间。
- 人工确认或修改发现，再提交到原环境服务。来源、采集时间和位置须明确声明或来自可信元数据。
- HAIDA保留离线演示标记；不把离线图自动定位到杭州，不伪称由某次仿真飞行拍摄。
- 验收：分析ID→发现ID→事件ID→任务ID→报告ID可追溯；误检能驳回、漏检可补充；重复导入不生成重复事件；后端核对权限、幂等和结案证据。
- 处置完成仍依赖人工提供后图与说明；模型摘要不能判定现实已经清理。

### P0-D：RAG证据与前端AI交互

- 围绕主线补充SOP、设备参数、产品限制和可公开核实的规则；保留来源、版本、适用范围和引用片段。
- 静态规则走RAG，实时任务/飞机/事件状态走Java查询，不把过期文档当当前运行状态。
- 建立独立保留问题集；根据错误分析再决定是否增加混合检索、重排或切片调整。
- 对话可点击引用；工具进度展示实际“查询资源/检索依据/生成方案”，不展示虚构内部思考。
- 验收：引用支持具体回答、查不到明确拒答、提示注入不能越权、断流可恢复、取消/重试有明确状态。

### P0-E：评价AI是否真正有效

建议初版准备50—100条锁定用例，按规则问答、实时查询、方案生成、信息不足、权限、注入与工具失败分类；数量是工程建议，不是赛事门槛。开发用例与最终报告集分开，改动后不挑选成功例作为全部结果。

| 对照 | 核心指标 |
| --- | --- |
| 手工页面操作 vs Agent辅助 | 完成率、耗时、点击数、人工修正次数 |
| 不检索 vs 检索增强 | 事实正确、引用支持、无依据拒答 |
| 无实时工具 vs 有实时工具 | 当前状态回答正确、不可执行方案是否被发现 |
| 原视觉模型 vs 改进模型 | 固定独立测试集Precision/Recall/mAP、复核负担、漏检情况 |

至少记录：用例ID、输入、模型/Prompt/知识库版本、数据快照或业务ID、工具调用、期望与实际结果、人工复核、端到端时延、token与估算费用。对同一输入可能不稳定的场景适当重复，报告失败率。现有200组调度结果是算法证据，不能替代Agent效果测评。

若能联系实际操作人员，做3—5次任务观察/访谈，记录角色、问题、操作时间及反馈；只能称小样本试用。没有客户或实际收入时如实描述，使用假设财务数据须标注。

### P0-F：可独立体验与可复现交付

- 准备生产构建、HTTPS反代、评审专用账号和隔离演示数据；按用户隔离上下文，限制频率和总预算。
- 首屏业务操作不等待完整3D资源；地图按需加载、低性能设备提供简化视图；测试弱网和普通笔记本。
- 合理区分模型推理资源校验与训练全量校验，继续固定模型/推理数据来源与哈希。现有只带132图的包不应为了新推理被迫恢复无关训练资源；此项需改设计并验证，不能直接跳过完整性检查。
- 给无CUDA环境提供经验证的CPU路径或明确的远程推理接入；记录实际耗时，不把旧结果播放当新推理。
- 在干净目录/另一电脑从README完成安装、登录、真实AI调用和一条业务闭环；保留错误及修复记录。
- 更新根README落后的技术栈和“Agent/识别待开发”描述，提供当前架构、权限、配置模板、模型与数据来源、复现命令、限制。
- 本轮建议建立仓库与发布方案，不自动公开当前目录；发布前先完成敏感配置和历史检查。

## 6. 演示和学习安排

建议7分钟视频：30秒用户痛点、45秒输入与图证、2分钟AI查证及方案卡、1分钟人工确认与仿真业务、1分钟拒绝/失败恢复、1分钟对照结果与部署、45秒边界及价值。总计7分钟。可以剪辑等待但注明；不把不同编号记录拼成一次闭环。

答辩至少能解释：为何AI优于固定按钮/模板、模型与规则各负责什么、RAG引用如何验证、模型错误如何拦截、如何防重复与越权、指标如何复现。官方允许AI辅助编程，但要求参赛者能解释代码逻辑。

下一小步建议只选“Agent读取待处理任务并生成方案卡”。业务用途是减少跨页面找任务/资源；数据流为Vue输入→Agent→受限工具→Java查询/方案→结构化卡片；学习点为工具输入输出契约及业务状态唯一归属。先让用户定义需要展示的字段和拒绝条件，再实现最小范围、运行验收；不要一次代写所有Agent或据此标记掌握。

第二步再接人工确认，第三步再接视觉分析ID。助手可承担样板代码、环境准备、回归与材料整理；用户的学习完成须以其实际实现、解释和运行证据记录。
